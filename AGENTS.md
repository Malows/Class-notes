# OpenCode Agent Guide for ClassNotes

## Commands

- Use pnpm only (`.npmrc` sets `engine-strict`; never npm/yarn).
- `pnpm dev` – Vite dev server. `pnpm build` runs `validate:i18n` **before** `vite build`, so keep i18n keys valid or the build fails.
- `pnpm check` – typecheck (`tsc --noEmit` + `svelte-check`). Requires `.svelte-kit` generated by `svelte-kit sync` (runs via `prepare` on install).
- `pnpm lint` (oxlint) / `pnpm format` (oxfmt).
- Tests (Vitest, jsdom, globals enabled): `pnpm test` runs **in watch mode** — for a one-shot run use `pnpm test:client` or `pnpm test:server`, or `pnpm exec vitest run <path>` for a single file. Tests are colocated as `*.test.ts` / `*.svelte.test.ts` (runes work in sidecar tests that keep the `.svelte` infix).

## Architecture (Svelte 5, runes forced)

- Data flow: route/component → client store → client service → thin `src/routes/api/v1/*/+server.ts` → server service → repository. Keep business logic out of components and API routes.
- `src/lib/client/` – browser-only: `components/`, `stores/` (runes classes in `.svelte.ts` files, provided to pages via Svelte context — `initStoreContext()` in `+layout.svelte`), `composables/`, `services/`, `utils/`.
- `src/lib/common/` – shared, env-agnostic: `types/` (plain TS + DTO types), `schemas/` (Zod, used on both client and server), `i18n/`, `constants/`. Never import `$lib/server/*` from client code.
- `src/lib/server/` – Node-only: `database/`, `repositories/` (Drizzle + better-sqlite3; own all SQLite access), `services/` (business rules).
- Client services call `apiFetch` from `src/lib/client/services/api.ts`, which hits `/api/v1/...` and unwraps the `{ data }` envelope; non-2xx throws `Error(result.error)`.
- The sidebar (`components/layout/sidebar/`) reads the **same context store instances pages use** (`getContext(StoreKey.*)`) and triggers guarded loads — don't wire it to the module-level store singletons, they are never populated.
- Prefer the matching store over prop drilling.

## Database (SQLite + Drizzle)

- Schema lives in `src/lib/server/database/schema.ts` (+ `relations.ts`); migrations under `database/migrations/` are applied automatically on fresh DB init (dev and test), then seeded. To reseed dev data, delete `class-notes.db*` and restart `pnpm dev` — no manual migration step.
- `drizzle-kit` v1 generates **one folder per migration** (`<timestamp>_<name>/migration.sql`), not flat `*.sql`. `applyDrizzleMigrations` reads both folder and legacy flat formats. `pnpm db:generate` works — `drizzle.config.ts` points at `schema.ts`.
- All entities use soft delete — every query filters `deletedAt IS NULL`; deletes set `deletedAt`.
- Tests run against an in-memory SQLite (`:memory:` via `VITEST`), so repository tests are real integration tests against the seeded schema.
- Periods are **shared across subjects**: one `periods` row per `(year, semester)`, linked via `subject_periods`. `(year, semester)` is globally unique (enforced by index). `create()` reuses an existing period and links the subject instead of duplicating; `update()` colliding with an existing combination returns 409 (`"Period already exists for this year and semester"`).
- Commissions have a required `subject_id`; creation threads subject + period, and the commissions page filters by both (`period_id` alone would leak commissions of other subjects sharing the period).

## i18n

- Files: `src/lib/common/i18n/{en,es}/*.json`, one JSON per namespace.
- `pnpm validate:i18n` (also runs on build) checks EN↔ES key parity and that every `$t('...')` literal used in code exists — run it after adding or renaming keys.

## Academic hierarchy

- `faculties` → `subjects` → (`subject_periods` ↔ `periods`) → `commissions`; `students` belong to commissions; `assignments` → `deliveries`.
- Changing the hierarchy means updating shared types + Zod schemas + stores + client/server services + repositories + migrations together.

## Workflow

- Env vars come from `.env` (see `.env.example`); Sentry/Plausible are optional and no-op when unset — don't add required env vars.
- Significant changes use OpenSpec: proposals under `openspec/changes/**`, specs under `openspec/specs/**`; completed work is archived to `openspec/changes/archive`. Local `opsx-*` commands and skills live in `.opencode/`.
- No CI is configured (`.github/workflows/` is empty) — run `pnpm check`, `pnpm lint`, and the relevant tests before committing.
