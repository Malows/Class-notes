# Proposal

## Why

The Docker deployment cannot run in production today: the compiled server never finds the SQL migrations (they are not in `build/`), the database path is inlined at build time so `-e` cannot redirect it, the configured `DATABASE_PATH` is never read, and the only way to get a usable schema is to boot with `NODE_ENV=development`, which also runs the demo seeder. Operators end up with a container whose database lives outside the volume, is wiped on every recreate, and looks "seeded" in production.

## What Changes

- Replace the single-stage Dockerfile with an explicit multi-stage build (deps → build → runtime) on a current Node LTS image (`node:26-alpine`) and pin pnpm to `12.23.0` instead of installing whatever `latest` is.
- Read the database location at **runtime** (`DATABASE_PATH`) instead of the build-inlined `DATABASE_NAME`, and mount it under `/app/data`.
- Ship the SQL migrations inside the runtime artifact and apply them as a **separate phase** before the server starts, with migration tracking so existing databases receive new migrations.
- Decouple demo seeding from boot: seeding never runs in production and only happens through an explicit opt-in (development/test or an explicit flag/command).
- Add a `.dockerignore` so local `node_modules`, `build`, `.svelte-kit`, `.env`, `*.db*` and coverage output stop leaking into the image build.
- Document the production run sequence (build image → migrate → serve) and the verification steps.
- **BREAKING**: production deployments must supply `DATABASE_PATH` (absolute path on the volume); the old `DATABASE_NAME`/`DATABASE_PATH` split disappears.
- Out of scope: `ORIGIN`/reverse-proxy tuning, TLS, and the stale `portable-infrastructure` single-binary requirement.

## Capabilities

### New Capabilities

- `production-deployment`: how the application is packaged and booted in production — multi-stage OCI image, Node LTS + pinned pnpm, runtime-configured SQLite path on a persistent volume, migrations applied at deploy time independently from demo data, and seeding disabled outside explicit opt-in.

## Impact

- `Dockerfile`, `docker-compose.yaml`, new `.dockerignore`, new runtime entrypoint/migration script.
- `src/lib/server/database/db.ts` (env source, boot responsibilities), `src/lib/server/database/migrate.ts` (migrations discovery + tracking).
- `package.json` (`packageManager`, scripts), `pnpm-lock.yaml` (regenerated by the pinned pnpm), `.env.example` (single `DATABASE_PATH`).
- `README.md` deployment section and `AGENTS.md` database/migration notes.
- Existing databases and the "delete the DB after a schema change" workflow are replaced by tracked migrations.
